# GitHub Actions で自動運用する

サーバーを用意せず、**GitHub Actions** をスケジューラ兼実行環境として完全自動運用する手順です。
ワークフローは `.github/workflows/scout.yml` です。

> まず必ず `dry_run=true`（実送信しない）で動作を確認してから本番に切り替えてください。

---

## ⚠️ 先に知っておくべき2つの注意点

GitHub Actions のランナーは**毎回まっさらな使い捨て環境**です。そのため次の2点に注意します。

1. **状態（送信履歴・再送予定・ログインセッション）の保持**
   重複送信の防止と再送スケジュールは `data/` 配下の SQLite DB に保存されます。本ワークフローは `actions/cache` で `data/` を実行間に引き継ぎますが、**キャッシュは最善努力**（約7日アクセスが無い／容量超過で消える）です。万一消えると重複判定がリセットされ、**同じ候補者へ再送信するリスク**があります。毎日実行していれば消えにくいですが、心配な場合はより確実な保存先（後述）をご相談ください。
   なお保存は**送信ステップの直後にも**行います（ピックアップ後・検索スカウト後・実行末尾の3回）。実行末尾のみの保存だと、送信後にタイムアウト等で中断された場合に**その日の送信記録が丸ごと巻き戻る**事故が起こるためです（2026-07 に4回発生・計56件。復元済み、`docs/スカウト分析.md` 参照）。

2. **ログイン（2FA・bot検知）**
   GitHub のデータセンターIPからの自動ログインは、ビズリーチの2段階認証やbot検知で失敗しやすいです。これを避けるため、**ローカルで一度ログインしたセッションを secret として持ち込む**方式を推奨します（下記 手順2）。それでも新しいIPからのアクセスは制限される場合があります。

## セットアップ手順

### 手順1: セレクタを設定してコミット
ビズリーチの実画面に合わせたセレクタを用意します（[セレクタ設定ガイド.md](セレクタ設定ガイド.md) 参照）。

```bash
cp config/bizreach_selectors.example.yaml config/bizreach_selectors.yaml
# 実画面に合わせて編集し、コミット（セレクタは機密ではないのでコミットしてOK）
git add config/bizreach_selectors.yaml && git commit -m "ビズリーチ セレクタ設定" && git push
```

### 手順2: ログインセッションを取得して secret 化（2段階認証がある場合のみ・推奨）

> **2段階認証を使っていない場合、この手順2は不要です。** ワークフローが手順3の
> メール/パスワードで自動ログインします。手順3へ進んでください。

2段階認証がある場合は、お手元のPCで一度だけログインし、そのセッションを GitHub に登録します。

```bash
pip install -e . && playwright install chromium
bizscout login            # ブラウザが開くのでログイン（2FAも手動入力）
# → data/sessions/bizreach_state.json が保存される
base64 -w0 data/sessions/bizreach_state.json   # 出力された文字列をコピー
```
コピーした文字列を、GitHub の **Settings → Secrets and variables → Actions → New repository secret** で
`BIZREACH_STORAGE_STATE_B64` という名前で登録します。

### 手順3: Secrets（機密情報）を登録
同じ画面で以下を登録します。

| Secret 名 | 内容 |
|---|---|
| `ANTHROPIC_API_KEY` | Claude APIキー |
| `BIZREACH_EMAIL` | ビズリーチ ログインメール（セッション失効時の再ログイン用） |
| `BIZREACH_PASSWORD` | ビズリーチ パスワード |
| `BIZREACH_STORAGE_STATE_B64` | 手順2 のセッション（**2段階認証がある場合のみ**。無ければ不要） |
| `GSHEET_SERVICE_ACCOUNT_B64` | スカウト分析（Google Sheets 連携）用のサービスアカウント鍵。**任意**・手順は `docs/スカウト分析.md` |

### 手順4: Variables（非機密の設定）を登録
**Variables** タブで以下を登録します（定期実行で使われます）。

| Variable 名 | 例 | 意味 |
|---|---|---|
| `BIZSCOUT_DRY_RUN` | `true` | **まず true。** 本番送信する時だけ `false` |
| `BIZSCOUT_SEARCH_URL` | `https://cr-support.jp/search?saved=...` | 対象候補者の保存検索URL（空なら再送のみ）。**複数指定する場合は半角スペース・改行・`\|` のいずれかで区切る（カンマは区切りとして扱われません）**。全ての保存検索が上から順に処理され、実行ログの `検索URL 2/4 を処理します。` とサマリの `保存検索 4 件` で読み込み件数を確認できます。同じ候補者が複数の検索に出ても重複送信はされません |
| `BIZSCOUT_MAX` | `30` | **保存検索1件あたり**の取り込み上限（検索スカウト用）。対象条件を満たさない候補者が大半なので、**送信したい件数より十分大きくしておく**（目安: 送信目標が20通なら 保存検索の数 × この値 が 40〜60 以上になるように）。送信合計は `BIZSCOUT_MAX_SENDS_PER_RUN` が上限で、そこに達した時点で取り込みも打ち切るため、大きくしても無駄な取り込みは発生しない。全ての保存検索を処理しても送信目標に届かなかった場合はログに警告が出る |
| `BIZSCOUT_REEVALUATE_AFTER_DAYS` | `30` | 直近この日数以内に**対象外と判定した**候補者は取り込みで読み飛ばし、検索結果の次ページへ進む（任意・未設定なら30）。送信済みは期間に関係なく常に読み飛ばす。対象条件を満たすのに未送信の候補者は読み飛ばさない（次回の実行で送るため）。**0 にすると毎回同じ先頭N件を取り直す**ため、通常は変更しない |
| `BIZSCOUT_INGEST_MAX_PAGES` | `20` | 上記の読み飛ばしで検索結果を辿る最大ページ数（1ページ=100件・任意・未設定なら20） |
| `BIZSCOUT_PICKUP_MAX` | `50` | ピックアップの最大処理件数（未設定なら50）。**本日の全ピックアップを開封（既読化）するため、日次の対象件数（通常10〜15件）より十分大きくしておく**。ピックアップ送信は無料枠のため `BIZSCOUT_MAX_SENDS_PER_RUN` の制限を受けず、対象条件を満たす全員へ送信される |
| `BIZSCOUT_MAX_SENDS_PER_RUN` | `20` | **1回の実行で送る初回スカウトの合計上限**。保存検索ごとではなく**全保存検索の合計**（4つ登録していても合計でこの件数まで）。この件数に達した時点で残りの保存検索は開かず、次回の実行に回す。再送にも同じ値が別枠で適用される。ピックアップは無料枠のため適用されない |
| `BIZSCOUT_MODEL` | `claude-opus-5` | 生成モデル（任意）。**Opus は Opus 5 を使う方針**のため、旧 Opus のモデル名が残っていても `claude-opus-5` に読み替えて実行します（`bizscout doctor` の「生成モデル」行に読み替えを表示） |
| `BIZSCOUT_GSHEET_SPREADSHEET_ID` | `1AbC...` | スカウト分析の出力先スプレッドシートID（**任意**・`docs/スカウト分析.md` 参照） |
| `BIZSCOUT_EXPECT_STATE` | `true` | **状態DB消失ガード。既定で有効**（Variable 未設定でも `true` として動きます）。送信履歴DBが空のまま実送信しようとしたら中断する（下記「状態DBが消えたときの復旧」参照）。**本当の初回運用のときだけ `false` を明示設定**する |

## 動かす

### 手動で試す（推奨の最初の一歩）
1. GitHub の **Actions** タブ → 左の **scout** → **Run workflow**
2. `dry_run` = `true`、`search_url` に保存検索URL、`max` に件数を入れて実行
3. 実行ログと、末尾の `Status report`（`bizscout report` 相当）で生成内容・状況を確認
4. `Upload logs` の成果物（artifact）で `data/exports/` の文面を確認できます

### 定期実行
`.github/workflows/scout.yml` の `schedule` は毎日 **16:09 JST（主）** と **18:39 JST（予備）** の2回起動します。
定期実行は Variables の値を使うため、`BIZSCOUT_DRY_RUN=true` の間は**送信されません**。

> **金土日・祝日・祝日の前日(JST)は通常スカウト（検索スカウト＋再送）を送信しません。**
> **ピックアップ（無料枠）は毎日送信します。** 通常スカウトが動くのは原則 月〜木 です。
> 金曜と祝日の前日を止めるのは「翌日から休みで読まれずに埋もれる」ためです。
> 判定は `config/scout_rules.yaml` の `schedule` セクションに基づき `bizscout check-schedule` が行います
> （祝日は振替休日・国民の休日も判定）。返信の自動検知・分析同期は休止日も通常どおり動きます。
> 手動実行（Run workflow）は明示操作のため対象外で、`mode=scout` を選べば休止日でも通常スカウトを送れます。
>
> 休止日の調整（`config/scout_rules.yaml`）:
> ```yaml
> schedule:
>   search_skip_weekdays: [5, 6, 7]  # 5=金, 6=土, 7=日（1=月）
>   search_skip_holidays: true       # 日本の祝日も休止
>   search_skip_holiday_eve: true    # 祝日の前日も休止（例: 火曜が祝日なら月曜を休止）
>   search_skip_dates: []            # 年末年始など追加の休止日（YYYY-MM-DD）
> ```
> 本日送信されるかは `bizscout check-schedule --kind search` で確認できます。

> GitHub の `schedule` は毎時00分が最も混雑し、数時間の遅延やまれにドロップが起こり得るベストエフォート仕様です。
> そのため実行時刻を00分から外し、さらに予備の時刻を用意して「その日ぜんぶ未実行」を防いでいます。
> 実測では設定時刻から1〜2.5時間ほど遅れて発火する傾向があったため、遅くなりすぎないよう
> 当初の19:09/21:39 JSTから3時間前倒しし、体感の到着時刻を17時台後半〜18時台に寄せています。
> 主・予備の両方が走っても、重複防止（SQLite）により二重送信にはなりません（予備は既送信分をスキップします）。
> 秒単位の時刻厳守が必要な場合は、外部スケジューラから `workflow_dispatch` API を叩く方式を検討してください。

### 本番送信に切り替える
1. 手動実行＋`dry_run=true` で文面と挙動に納得できたら
2. Variables の `BIZSCOUT_DRY_RUN` を `false` に変更
3. 以降の定期実行（または `dry_run=false` の手動実行）で実送信されます

---

## 止め方（緊急停止）
- いますぐ止める: 実行中なら Actions 画面で該当 run を **Cancel**
- 当面止める: Variables の `BIZSCOUT_DRY_RUN` を `true` に戻す（送信されなくなる）
- 完全に止める: Actions タブで **scout** ワークフローを **Disable**

## 状態DBが消えたときの復旧

重複防止・再送予定は `data/bizscout.db`（SQLite）に保存され、`actions/cache` で実行間に引き継がれます。
キャッシュはベストエフォートのため、**約7日アクセスが無い・容量超過などで消える**ことがあります。
消えたまま実送信すると、全候補者が「初回」と誤判定され**全員へ再送信**してしまいます。

これを防ぐ仕組みと、消えた場合の復旧手順は次のとおりです。

### 自動復元（毎実行・`bizscout restore-state`）
毎回の実行は送信より前に `bizscout restore-state` を実行し、**実行ログ由来の復元表**
（`config/sent_backfill.json`）から送信履歴（`scouts` / `sent_log`）を再構築します（冪等）。
キャッシュが丸ごと消えても、復元表に載っている送信までは**自動で復元**され、
重複送信防止と週次サマリの分母が保たれます。
復元表は実行ログの「初回送信完了」「再送完了」行から機械的に抽出した事実のみを収録します。
新しい送信はDBに直接記録されるため復元表への追記は不要ですが、**キャッシュ消失が起きた後は**
その時点までの送信を復元表へ追記しておくと、以後の全損にも耐えられます（追記方法は
`docs/スカウト分析.md` 参照）。

### 自動ガード（`BIZSCOUT_EXPECT_STATE`・既定で有効）
**送信履歴DBが空のまま実送信しようとした瞬間に実行を中断**します（`RuntimeError` で job が赤くなる）。
これにより「キャッシュ消失 → 気づかず全員へ再送信」という事故を未然に止めます。
`dry_run=true` の実行はそもそも送信しないためガード対象外です。

加えて起動前チェック（doctor）でも同じ条件を fail として検出し、送信だけでなく
**状態の保存もシート同期も止めます**。以前は空の状態でも実行末尾の保存が走り、
空の `data/` が「最新の保存」としてキャッシュに書き込まれて、正常なキャッシュを
覆い隠していました（2026-08-17 に発生。復元表に無い送信記録がシートから消えました）。
現在は doctor 通過後にだけ保存を許可しています（ワークフローの `STATE_OK` ゲート）。

ワークフローの env で既定 `true` を渡しているため、Variable を設定しなくても有効です
（本当の初回運用のときだけ Variables に `false` を明示設定してください）。
実際に効いているかは毎回の実行ログの起動前チェック「送信の安全弁」行で確認できます
（`状態DB消失ガード=有効` と出ます）。以前はこの Variable がワークフローに渡っておらず、
手順書どおりに設定しても**CIでは常に無効**でした（2026-08-13 修正）。

### DBスナップショットからの復旧（mode=restore-db・推奨）
本ワークフローは毎回の実行で `data/bizscout.db` を `Upload logs` の成果物（artifact, **14日保持**）に含めています。
復元表でカバーしきれない分（送信した文面の件名・候補者プロフィール・返信の記録）も
スナップショットには残っているため、**巻き戻りが起きたら最優先でこちらを使ってください**。

1. GitHub の **Actions** タブ → **消失前の最後に正常だった run** を開き、URL 末尾の run ID を控える
   （例: `.../actions/runs/32124592882` なら `32124592882`）
2. **Actions → scout → Run workflow** で次を指定して実行する
   - `mode` = `restore-db`
   - `restore_run_id` = 手順1で控えた run ID
   - `dry_run` = `true`（復旧だけを行い、送信はしない）
3. ログの「DBマージ完了: …」行で取り込み件数と、`初回送信 計N件・返信あり 計M件` を確認する
4. 件数が妥当なら、通常どおりの定期実行に戻す

取り込みは**現行の記録を壊しません**。欠けている行の追加が基本で、例外は次の2つだけです。

- 同じ人が両方にある場合、初回送信日は**古い方（真の初回）**を採る（巻き戻り中の重複送信で
  日付が後ろにずれたケースの是正）
- 返信は「未返信 → 返信あり」の**昇格のみ**（返信ありを取り消さない）

何度実行しても結果は同じ（冪等）なので、迷ったら実行して構いません。
復旧すると送信済みの**件名が戻る**ため、受信箱スキャンによる返信の自動検知も次回実行から復活します。

> ローカルで作業したい場合は、artifact を展開して `bizscout merge-db --from <展開した bizscout.db>` を直接実行できます。

### 手作業でDBを差し替える場合
`mode=restore-db` が使えない事情があるときは、artifact の `data/bizscout.db` を取り出して
ローカルの `data/` に配置し、`bizscout report` で件数が妥当か確認したうえで、
キャッシュに載る形（次回実行時に `actions/cache` が拾える状態）で用意します。
復元後は `BIZSCOUT_DRY_RUN=true` で1回手動実行し、`Status report` の件数分布が
消失前と同傾向であることを確認してから本番送信に戻してください。

> 復旧に自信が持てないときは、`BIZSCOUT_DRY_RUN=true`（または `BIZSCOUT_EXPECT_STATE=true` のまま）にしておけば実送信は止まります。慌てて `false` に戻さないでください。

## より確実な状態保存（任意）
`actions/cache` ではなく、より確実な状態保存（例: 専用ブランチや外部DBへの保存、暗号化したうえでのコミット）に切り替えられます。ご希望があれば、運用に合わせて実装します。
